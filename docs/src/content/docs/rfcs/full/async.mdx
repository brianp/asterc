## 1. Design Principles

- Async is an execution strategy, not a type signature — no viral async
- The caller decides how to invoke a function — sync, async, or resolve
- The runtime is invisible — developers never initialize or manage it
- Green threads, not futures/state machines — every function can suspend
- Data races are warned, not blocked — the compiler warns you, it doesn't block you
- One concurrency model — no split between sync and async worlds

---

## 2. Runtime Model

### Green Threads

Aster uses stackful green threads (M:N scheduling). Each green thread has
its own small stack (~2-8KB, grows on demand) and can be suspended and
resumed at any point.

The runtime multiplexes green threads onto a pool of OS threads. The
developer never sees OS threads, schedulers, or runtimes.

### Work-Stealing Scheduler

Each OS thread has a local run queue (double-ended queue). When a thread's
queue is empty, it steals work from another thread's queue (takes half).
This self-balances across cores.

The scheduling loop per OS thread:
1. Check local queue — run a green thread if available
2. Check global queue — steal a batch if available
3. Steal from another thread's local queue
4. Nothing to do — poll for I/O or park

### OS Thread Pool

Default: one OS thread per CPU core. Configurable at runtime via the
`ASTER_OS_THREADS` environment variable. Not configurable at compile time —
the binary adapts to the deployment environment.

```
# Auto-detects cores
./my_app

# Override for specific deployments
ASTER_OS_THREADS=4 ./my_app
```

### Runtime Startup

Implicit. The runtime (thread pool, scheduler, I/O poller) initializes
before `main()` runs. `main()` itself executes on a green thread. The
developer never initializes or configures a runtime.

### Yield Points

The compiler inserts preemption checks at:
- **Function calls** — every call is a potential yield point
- **Loop back-edges** — top of every `while`/`for` iteration

Each check reads a scheduler-set flag: "have you been running too long?"
If yes, the green thread yields to the scheduler. Cost: one memory read
per check. Negligible.

This is cooperative preemption — technically cooperative, but the compiler
handles it automatically. From the developer's perspective it's preemptive.

### I/O Suspension

When a green thread performs I/O:

**Network I/O:**
1. Runtime calls non-blocking `read()`/`write()` on the socket
2. If data is available — return immediately, no suspension
3. If not available — register the file descriptor with the I/O poller
   (epoll on Linux, kqueue on macOS, IOCP on Windows), suspend the
   green thread
4. OS thread picks up another green thread from its queue
5. When data arrives, the I/O poller wakes the green thread — it goes
   back on a run queue and resumes where it left off

**Disk I/O:**
Disk reads don't work with epoll/kqueue (they return "ready" immediately
then block anyway). Disk I/O is dispatched to a small pool of dedicated
OS threads that perform blocking reads. When the read completes, the
green thread is woken.

**The developer sees none of this.** They write `file.read()` or
`socket.read()` and the runtime picks the right mechanism.

### Standard Library and Async

Standard library functions are always synchronous. They know nothing about
async. If a developer wants concurrency, they wrap calls at the call site
with `async` or `resolve`. The runtime handles suspension transparently
when I/O occurs inside any function.

## 3. Invocation Modes

Every function in Aster is a plain function. The caller chooses the
execution strategy:

| Mode | Syntax | Returns | Behavior |
|------|--------|---------|----------|
| Sync | `f()` | `T` | Runs on current green thread, sequentially |
| Blocking | `blocking f()` | `T` | Calls suspendable work and waits without exposing `Task[T]` |
| Async | `async f()` | `Task[T]` | Spawns new green thread, returns handle |
| Resolve | `resolve task` | `T` | Consumes an existing `Task[T]`, suspending until it finishes |

### Sync — `f()`

Plain function call. Runs on the current green thread. It is only valid
for non-suspendable callees. If a callee can suspend, the caller must
write `blocking f()` or `async f()` explicitly.

```
let user = fetch_user(1)    # sequential, returns User
```

### Blocking — `blocking f()`

Calls suspendable work and waits for its result without materializing a
user-visible `Task[T]`. The current green thread may suspend while the
callee runs, but the call still returns `T` directly.

```
let user = blocking fetch_user(1)    # waits, returns User
```

### Async — `async f()`

Spawns a new green thread to run `f()`. Returns immediately with a
`Task[T]` handle. The work runs concurrently.

```
let task = async fetch_user(1)    # returns Task[User] immediately
# fetch_user is running on another green thread
# execution continues here
```

### Resolve — `resolve task`

Suspends the current green thread until a task completes. Always
requires `!` because any task can be cancelled (CancelledError).

```
let task = async fetch_user(1)
# ... do other work ...
let user = resolve task!          # suspend until task finishes
```

The current green thread is parked (not burning CPU). The OS thread picks
up other green threads. When the result is ready, the green thread resumes.

### Detached — `detached async f()`

Spawns a green thread with no handle. Fire-and-forget. The developer
can't retrieve the result or check status.

```
detached async cleanup_old_sessions()
```

If the detached function throws, the error is logged and the program
continues. The error has nowhere to propagate.

`detached` is an explicit opt-out of structured concurrency. It must be
intentional — the must-consume rule (section 4) prevents accidental
fire-and-forget.

## 4. Task[T]

`Task[T]` is a handle to a green thread that will produce a value of
type `T`.

### Instance Methods

| Method | Returns | Purpose |
|--------|---------|---------|
| `.is_ready()` | `Bool` | Non-blocking status check |

### Consuming a Task

`resolve task` consumes an existing `Task[T]`, suspends the current green
thread until the task completes, then returns `T`.

```
let task = async fetch_user(1)
let user = resolve task!
```

If the task is already complete, `resolve` returns immediately.

`resolve` is not a call-site form for ordinary functions. It is only for
joining `Task[T]` handles.

### Must-Consume Rule

Dropping a `Task[T]` without consuming or detaching it is a **compile
error**. This prevents orphaned green threads.

```
let t = async fetch_user(1)
# ... never use t ...
# COMPILE ERROR: task 't' is never consumed
```

You must either:
- `resolve` the task
- Pass it to `resolve_all` or `resolve_first`
- The scope exits and structured concurrency handles cleanup

### Task Utilities

Standalone functions for working with multiple tasks. All tasks must be
the same type.

**`resolve_all(tasks)` — wait for all:**
```
let tasks = [async fetch_user(1), async fetch_user(2), async fetch_user(3)]
let users = resolve_all(tasks)    # List[User]
```

All tasks run concurrently. Returns when all are complete.

**`resolve_first(tasks)` — wait for fastest:**
```
let tasks = [async fetch_from_primary(), async fetch_from_backup()]
let data = resolve_first(tasks)    # T — whichever finishes first
```

Returns the first result. Cancels all remaining tasks.

## 5. Async + Error Handling

Error handling composes naturally with async. The rules follow from the
error handling RFC — `!` propagates, `!.catch` matches, `!.or()` provides
defaults.

### `resolve` always requires `!`

`resolve` is always a throwing operation because any task can be
cancelled — via scope exit, `resolve_first`, or explicit `.cancel()`.
Cancellation produces `CancelledError`. This applies regardless of
whether the underlying function throws.

```
# Non-throwing function — resolve still requires !
def add(a: Int, b: Int) -> Int

let task = async add(a: 1, b: 2)
let sum = resolve task!                         # propagate CancelledError
let sum = resolve task!.or(0)                   # default if cancelled
let sum = resolve task!.catch
  CancelledError _ -> 0
```

```
# Throwing function — CancelledError joins the function's errors
def fetch(url: String) throws NetworkError -> String

let task = async fetch(url: url)
let data = resolve task!                        # propagate any error
let data = resolve task!.or("")                 # default on any failure
let data = resolve task!.catch
  CancelledError _ -> "cancelled"
  NetworkError n -> n.message()
```

### `resolve_all` + `throws`

If any task threw or was cancelled, `resolve_all` throws. All tasks are
resolved — errors surface after completion.

```
let tasks = [async fetch(url1), async fetch(url2)]
let results = resolve_all(tasks)!    # throws if any task threw or was cancelled
```

### `resolve_first` + `throws`

If the winning task threw, `resolve_first` throws. Losing tasks are
cancelled (their CancelledErrors are not surfaced — only the winner matters).

```
let first = resolve_first(tasks)!.catch
  CancelledError _ -> ""       # winner was cancelled before finishing
  NetworkError n -> ""
```

### `detached async` + `throws`

Detached tasks that throw log the error and continue. The error has
nowhere to propagate.

```
detached async cleanup()    # if cleanup throws, error is logged
```

For managed restarts of detached tasks, see the supervised tasks RFC.

## 6. Structured Concurrency

### Async Scope

`async scope` creates a lifetime boundary. All tasks spawned within the
scope must complete or be canceled before the scope exits.

```
async scope
  let t1 = async fetch_user(1)
  let t2 = async fetch_user(2)
  let t3 = async fetch_user(3)

  let u1 = resolve t1!
  let u2 = resolve t2!
  let u3 = resolve t3!

  process(u1, u2, u3)
# scope exits — all tasks guaranteed complete
```

### Scope Exit Cleanup

**When execution leaves a scope for any reason — normal completion, error
propagation, return, break — all unresolved tasks in that scope are
canceled.** This is non-negotiable. No orphaned green threads.

```
async scope
  let t1 = async fetch_user(1)
  let t2 = async fetch_user(2)

  let u1 = resolve t1!    # throws — propagates out of scope
  # t2 is CANCELED — scope exit cleans up unresolved tasks
  let u2 = resolve t2     # never reached
```

Errors within a scope follow normal error handling. If an error is caught
locally, the scope continues:

```
async scope
  let t1 = async fetch_user(1)
  let t2 = async fetch_user(2)

  let u1 = resolve t1!.or(default_user())  # handled — scope continues
  let u2 = resolve t2!                      # still runs
  process(u1, u2)
```

### Cancellation Mechanics

Cancellation is cooperative. When a green thread is canceled:

1. A cancellation flag is set on the green thread
2. At the next yield point (function call, loop back-edge, I/O), the
   flag is checked
3. The green thread runs cleanup (destructors/Close trait)
4. The green thread exits

A green thread can't be yanked mid-operation. It finishes its current
work and stops at a safe point. No corrupted state.

### CancelledError

When a task is cancelled and subsequently resolved, it throws
`CancelledError` (extends `Error`). Because any task can be cancelled
(via scope exit, `resolve_first`, or explicit `.cancel()`), `resolve`
on a task handle always requires `!` — even for non-throwing functions.

```
# Even a pure function can be cancelled
def add(a: Int, b: Int) -> Int

let task = async add(a: 1, b: 2)
task.cancel()

resolve task!.catch
  CancelledError _ -> log(message: "task was cancelled")
```

```
# Throwing functions — CancelledError is one of the possible errors
def fetch(url: String) throws NetworkError -> String

let task = async fetch(url: url)

resolve task!.catch
  CancelledError _ -> log(message: "task was cancelled")
  NetworkError n -> log(message: n.message())
```

`CancelledError` is a built-in error type. It integrates with `!`,
`!.catch`, `!.or()`, and `!.or_else()` like any other error.

### Cleanup Traits

- **`Drop`** — synchronous cleanup. Free memory, release locks. Runs
  during stack unwinding. Cannot perform I/O.
- **`Close`** — async-capable cleanup. Close database connections, flush
  buffers to disk. Runs on the green thread before it exits. Can perform
  I/O (the green thread is still alive during Close).

Cleanup runs in reverse order (last created, first cleaned up). If cleanup
itself throws, the error is logged and cleanup continues. Cleanup errors
never propagate.

## 7. Data Sharing Between Green Threads

### The Core Rule

When data crosses a thread boundary (`async`, `Shared`, `Channel`), it is
**shallow copied** by default. The compiler warns when the original
variable is used after being passed to a thread boundary.

```
let user = fetch_user(1)
let task = async save_user(user)

# warning: 'user' has been copied to an async context.
#          Mutations to 'user' will not affect the async task.
#          allow(copied_non_shared_resource) to suppress.

user.name = "Rick"     # works, but only affects local copy
```

**No warning when the variable isn't used again:**
```
let user = fetch_user(1)
let task = async save_user(user)
# user never referenced again — no warning
```

### Warning Scope

The compiler detects cases at the local scope level (levels 1-2):
- Variable used after being passed to `async`
- Variable used after being passed to `Shared()`
- Variable used after being passed to `channel.send()`

Deep alias tracking across functions, structs, and modules isn't
performed. For now, the compiler catches the common local cases and
tells the developer what's happening. More advanced analysis may come
later.

### Explicit Copy

When you want an independent copy intentionally:

```
let task = async process(user.copy())    # explicit deep copy
log(user.name)                           # no warning — original unaffected
```

### Mutex[T] — Shared Mutable State

For state that must be shared and mutated across green threads, use
`Mutex[T]`.

```
let state = Mutex(GameState(
  players: [p1, p2, p3],
  scores: Map(...)
))
```

**Scoped lock access:**

```
state.lock(s ->
  s.players[0].score = 100
  s.scores.set("alice", 100)
)
# lock automatically released
```

**Rules:**
- `.lock()` acquires the mutex and provides direct access to the data
- Nothing obtained inside `.lock()` can escape the block — the compiler
  enforces this. Assigning lock-scoped references to outer variables or
  returning them is a compile error
- Mutations inside `.lock()` are direct (no deep copy overhead)
- Lock is released automatically when the block exits

**Lock Timeout:**

All locks have a timeout. No infinite deadlocks by design.

```
# Default timeout (configurable globally)
state.lock(s ->
  s.players[0].score = 100
)

# Explicit timeout
state.lock(timeout: 5000, s ->
  s.players[0].score = 100
)
```

If the timeout expires, `lock()` throws `LockTimeoutError`. Handle with
normal error handling:

```
state.lock(s ->
  s.players[0].score = 100
)!.catch
  LockTimeoutError e -> log("couldn't acquire lock")
```

Default timeout is configurable at the runtime/project level.

### Manual Mutex API

The scoped `.lock()` block is the safe default. For advanced use cases,
manual lock/unlock is available:

```
state.acquire()
# do stuff with state.value
state.release()
# if you forget release... deadlock (until timeout)
```

Sharp knife, available, not the default.

## 8. Channels

Channels are typed pipes for passing messages between green threads.

### Channel Types

| Type | Senders | Receivers |
|------|---------|-----------|
| `Channel[T]` | One | One |
| `MultiSend[T]` | Many | One |
| `MultiReceive[T]` | One | Many |

### Creating Channels

```
# Default buffer size (configurable globally)
let ch = Channel[User].new()

# Explicit buffer size
let ch = Channel[User].new(capacity: 100)
```

All channels are buffered. No unbuffered channels.

### Three-Tier API

Consistent across send and receive:

**Send:**

| Method | Behavior | Returns |
|--------|----------|---------|
| `ch.send(value)` | Fire and forget. Drops if buffer full. | `Void` |
| `ch.wait_send(value)` | Suspends green thread until space available. | `Void` |
| `ch.try_send(value)` | Throws `ChannelFullError` if buffer full. | `throws` |

**Receive:**

| Method | Behavior | Returns |
|--------|----------|---------|
| `ch.receive()` | Returns immediately. Nil if empty. | `T?` |
| `ch.wait_receive()` | Suspends green thread until data available. | `T` |
| `ch.try_receive()` | Throws `ChannelEmptyError` if empty. | `throws` |

### Usage Examples

```
# Fire and forget
ch.send(user)

# Check and move on
let user = ch.receive()
match user
  nil => log("nothing yet")
  u => process(u)

# Suspend until ready
ch.wait_send(user)
let user = ch.wait_receive()

# Fail fast
ch.try_send(user)!.catch
  ChannelFullError e -> log("backed up")

let user = ch.try_receive()!.catch
  ChannelEmptyError e -> log("empty")
```

### Closing Channels

```
ch.close()
```

After closing:
- `send()` / `wait_send()` / `try_send()` throw `ChannelClosedError`
- `receive()` returns remaining buffered items, then `nil` when drained
- `wait_receive()` returns remaining items, then throws `ChannelClosedError`
- `try_receive()` returns remaining items, then throws `ChannelEmptyError`

### Data Ownership

Sending through a channel follows the same rule as all thread boundaries:
shallow copy, compiler warns if the original is used after sending.

```
let user = fetch_user(1)
ch.send(user)
user.name = "Rick"     # warning: copied to channel context
```

## 9. Summary of Decided Design

### Runtime
1. Green threads with stackful coroutines (~2-8KB stack, grows on demand)
2. M:N scheduling with work-stealing across OS threads
3. OS thread pool defaults to CPU core count, `ASTER_OS_THREADS` to override
4. Runtime starts implicitly before `main()` — invisible to developer
5. `main()` runs on a green thread
6. Compiler inserts yield checks at function calls and loop back-edges
7. I/O suspension: epoll/kqueue for network, thread pool for disk
8. Standard library functions are always synchronous

### Invocation Modes
9. `f()` — sync, runs on current green thread
10. `async f()` — spawns green thread, returns `Task[T]`
11. `resolve task!` — suspends until task complete, always requires `!`
12. `detached async f()` — fire-and-forget, no handle

### Task Interface
13. `Task[T]` with `.is_ready()` for non-blocking status check
14. `resolve task` to consume — suspends if not ready
15. Must-consume rule — dropping a task is a compile error
16. `resolve_all(List[Task[T]])` — wait for all, returns `List[T]`
17. `resolve_first(List[Task[T]])` — wait for fastest, cancel rest
18. No `.then()` — use sequential code + `resolve` instead

### Error Handling
19. `resolve task` always requires `!` — any task can be cancelled (CancelledError)
21. `resolve_all` throws if any task threw or was cancelled
22. `resolve_first` throws if the winning task threw; losers cancelled silently
23. `detached async` on throwing functions logs errors, continues

### Structured Concurrency
24. `async scope` creates a lifetime boundary for tasks
25. Scope exit (any reason) cancels all unresolved tasks — non-negotiable
26. Cancellation is cooperative — flag checked at yield points
27. Cancelled tasks throw `CancelledError` on `resolve` — all task resolves require `!`
28. `Drop` for sync cleanup, `Close` for async-capable cleanup
29. Cleanup errors are logged, never propagated

### Data Sharing
29. Thread boundaries shallow copy data by default
30. Compiler warns when original variable used after copy (local scope)
31. `allow(copied_non_shared_resource)` to suppress warning
32. Deeper alias tracking noted as future static analysis improvement
33. `Mutex[T]` for shared mutable state with scoped `.lock()` block
34. Nothing escapes `.lock()` — compiler enforced
35. All locks have timeouts — no infinite deadlocks
36. `LockTimeoutError` thrown on timeout
37. Manual `acquire()`/`release()` available for advanced use

### Channels
38. Three types: `Channel[T]`, `MultiSend[T]`, `MultiReceive[T]`
39. Always buffered, configurable capacity
40. Three-tier API: fire-and-forget, suspend, throw
41. `send()` drops on full, `receive()` returns `T?`
42. `wait_send()`/`wait_receive()` suspend until ready
43. `try_send()`/`try_receive()` throw on failure
44. `close()` signals no more data
45. Channel data follows same shallow copy + warning rules

## 10. What Was Rejected

- Tokio/futures/state machines as runtime model
- Explicit runtime initialization
- `await` keyword (replaced by `resolve`)
- `blocking` keyword (replaced by `resolve`)
- `.then()` chaining on tasks (use sequential code instead)
- Deep copy at thread boundaries (shallow copy + warnings instead)
- Rust-style borrow checker for thread safety (compiler warnings instead)
- Unbuffered channels
- Many-to-many channels

## 11. Deferred

- Supervised tasks — automatic restart with backoff for detached tasks
  (see supervised-tasks-rfc.md)
- Advanced static analysis for deep alias tracking across functions and
  modules
- `Drop` and `Close` trait detailed design
- Send/Share auto-derivation rules
