## Amendment (2026-08-12): Arity-1 Named Arguments

The original rule below says names are always required. That's now refined, keyed off the callee's **declared parameter or field count**: a callee that declares exactly one parameter (functions, methods, lambdas) or exactly one field (constructors) may be called with a single unnamed argument. A callee that declares two or more parameters or fields requires a name on every argument, at every call-site arity. This applies uniformly to functions, methods, and constructors.

The reasoning: labels exist to disambiguate between parameters. With one declared parameter there's nothing to disambiguate, so `say(hello)` can't be wrong the way `Point(1, 2)` can (transposed fields that still compile). At two or more declared parameters the label is exactly what catches silent transposition, which is the failure mode this convention exists to prevent. Keying off the declared count rather than the number of arguments passed keeps the rule stateable in one line — one param, positional OK, else name it — and preserves that transposition safety as a signature evolves: adding a second parameter (even a defaulted one) flips the callee into the names-required regime, so `Config(name, timeout = 30)` must be called `Config(name: "prod")`, never `Config("prod")`.

Three consequences:

- The explicit label stays legal at arity 1. `say(message: hello)` and `say(hello)` are both valid.
- A 2+-parameter callee rejects a lone positional even when the remaining parameters have defaults, because the rule keys off declared count, not arguments supplied.
- Constructors had drifted into accepting positional arguments at any arity, contradicting this RFC. That acceptance tightens to the same declared-count rule: a single-field class takes a lone positional, a multi-field class requires names.

This supersedes the earlier three-positional-arguments rule (issue #30), which was removed in favor of full consistency before this refinement. Tracked in [#52](https://github.com/brianp/asterc/issues/52); implementation plan: `docs/plans/completed/arity-1-args.md`.

## 1. Design Principles

- Standard protocols are how user types become first-class citizens of the language
- Operators (`==`, `<`, `>`) and constructs (`for`, string interpolation) desugar to protocol methods
- One way to do things — each protocol has exactly one shape
- Implement on the type you own — never modify foreign types
- Auto-derive where the compiler can generate a correct implementation
- Hash is not a protocol — it's an invisible consequence of Eq
- Named arguments are required everywhere — functions and constructors use the same calling convention

## 2. Prerequisites: Parametric Traits, Self, Named Arguments

### Parametric Traits

Traits can be parameterized by types:

```
trait Into[T]
  def into() -> T

trait Iterable[T]
  def each() -> Iterator[T]
```

A class can include the same trait multiple times with different type
parameters:

```
class Celsius includes Into[Fahrenheit], Into[Kelvin]
  value: Float

  def into() -> Fahrenheit
    Fahrenheit(value: value * 9.0 / 5.0 + 32.0)

  def into() -> Kelvin
    Kelvin(value: value + 273.15)
```

When multiple parametric trait inclusions produce methods with the same
name and arity, the compiler resolves by expected type at the call site
(see section 3).

### Self Type in Traits

Traits can use `Self` to refer to the implementing type:

```
trait Eq
  def eq(other: Self) -> Bool
```

When `Point includes Eq`, `Self` becomes `Point`. The compiler enforces
that `eq` takes a `Point`, not any arbitrary `Eq` type.

### Named Arguments Everywhere

> Amended 2026-08-12: labels are optional when the callee declares exactly one parameter or field. See the amendment at the top of this RFC.

All function calls and class construction use named arguments. Names are
always required. Argument order at the call site does not matter — the
compiler matches by name.

```
# Function calls
connect(url: "localhost", retries: 5, timeout: 60)
log(message: "hello")
rgb(r: 255, g: 128, b: 0)

# Class construction
User(name: "Alice", email: "a@b.com")
Config(timeout: 60, retries: 5)

# Order doesn't matter — matched by name
rgb(b: 0, r: 255, g: 128)
```

This replaces the previous design where functions used positional
arguments and only class construction used named fields. The change
ensures one calling convention everywhere — no ambiguity between
function calls and construction.

The 3-argument limit (configurable) still applies. Default parameter
values still work:

```
def connect(url: String, retries: Int = 3, timeout: Int = 30) -> Connection

connect(url: "localhost")                    # uses defaults
connect(url: "localhost", timeout: 60)       # override one default
```

## 3. From / Into — Type Conversion

### The Problem

Types need to convert to other types. The conversion protocol must work
regardless of which side you own — the source type or the target type.

### Two Traits, Two Directions

**`Into[T]`** — include on the source type you own. Instance method.

```
trait Into[T]
  def into() -> T
```

**`From[T]`** — include on the target type you own. Construction protocol.

```
trait From[T]
  def from(value: T) -> Self
```

### Into — When You Own the Source

```
class Celsius includes Into[Fahrenheit]
  value: Float

  def into() -> Fahrenheit
    Fahrenheit(value: value * 9.0 / 5.0 + 32.0)

# Usage
let temp: Fahrenheit = celsius.into()
take_fahrenheit(temp: celsius.into())
```

When a class includes multiple `Into[T]` with different type parameters,
the compiler resolves `.into()` using the expected type at the call site.
If the expected type is ambiguous, the compiler reports an error asking
for a type annotation.

### From — When You Own the Target

`From[T]` is a construction protocol. The `from` method is not an
instance method and not a class method — it is a compiler intrinsic
invoked via `Type.from(value: x)` syntax, in the same category as
introspection intrinsics (`Type.fields`, `Type.ancestors`).

```
class User includes From[PgRow]
  name: String
  email: String

  def from(row: PgRow) -> Self
    User(name: row.get(key: "name"), email: row.get(key: "email"))

# Usage — compiler intrinsic invocation
let user = User.from(value: pg_row)
```

### Auto-Derived Reverse

When `User includes From[PgRow]`, the compiler automatically enables
`pg_row.into()` in contexts where `User` is expected. This does not
modify `PgRow` — the resolution lives in the conversion protocol, not
on the foreign type's method table.

```
# All three work
let user = User.from(value: pg_row)         # From — explicit
let user: User = pg_row.into()              # Into — expected type
take_user(user: pg_row.into())              # Into — argument type
```

### From as the Only Custom Initializer

`From[T]` is the only path to custom initialization. There are no
custom constructors. Want a custom way to build a `User`? Define a
type for the input:

```
class UserFromCSV
  row: String

class User includes From[PgRow], From[UserFromCSV]
  name: String
  email: String

  def from(row: PgRow) -> Self
    User(name: row.get(key: "name"), email: row.get(key: "email"))

  def from(csv: UserFromCSV) -> Self
    let parts = csv.row.split(sep: ",")
    User(name: parts.get(index: 0).or(default: ""), email: parts.get(index: 1).or(default: ""))

# Construction is always field construction
User(name: "Alice", email: "a@b.com")

# Conversion is always From
User.from(value: pg_row)
User.from(value: UserFromCSV(row: "alice,a@b.com"))
```

No ambiguity at any call site. Field construction and From conversion
are syntactically distinct.

### Fallible Conversion — No TryFrom / TryInto

Aster's `throws` mechanism handles fallible conversion. No separate
traits needed:

```
class Celsius includes Into[Fahrenheit]
  value: Float

  def into() throws ConversionError -> Fahrenheit
    if value < -273.15
      throw ConversionError(message: "below absolute zero")
    Fahrenheit(value: value * 9.0 / 5.0 + 32.0)

# Caller handles the error with standard ! / !.catch / !.or
let temp: Fahrenheit = celsius.into()!
let temp: Fahrenheit = celsius.into()!.or(default: Fahrenheit(value: 0.0))
```

### Stdlib Conversions

Primitives include standard conversions:

- `Int includes Into[Float]`, `Into[String]`
- `Float includes Into[Int]` (truncating, via `throws`), `Into[String]`
- `String includes Into[Int]` (parsing, via `throws`), `Into[Float]` (parsing, via `throws`)
- `Bool includes Into[String]`, `Into[Int]`

## 4. Eq — Equality

### Trait Definition

```
trait Eq
  def eq(other: Self) -> Bool
```

### Operator Desugaring

- `a == b` desugars to `a.eq(other: b)`
- `a != b` desugars to `not a.eq(other: b)`

`!=` is always the negation of `==`. There is no way to define them
independently.

### No PartialEq

Rust splits `PartialEq` and `Eq` because of IEEE 754 NaN where
`NaN != NaN`. Aster has one trait. Float's `eq` follows IEEE 754
behavior — `NaN.eq(other: NaN)` returns `false`. This is documented
behavior of `Float`, not a type-system concern.

### Auto-Derive

When a class writes `includes Eq` without defining `eq()`, the compiler
generates a field-by-field comparison. All fields must include `Eq`.

```
class Point includes Eq
  x: Int
  y: Int
# compiler generates: eq checks x == other.x and y == other.y

class User includes Eq
  id: Int

  def eq(other: User) -> Bool
    id == other.id
# manual: only compares id
```

### Foreign Type Diagnostic

When auto-derive fails because a field's type is foreign and lacks `Eq`:

```
Error[E025]: cannot derive Eq for `UserProfile`
  --> src/models/profile.aster:3:3
  |
3 |   avatar: cdn.Avatar
  |   ^^^^^^^^^^^^^^^^^ `cdn.Avatar` does not include Eq
  |
  = note: `cdn.Avatar` is defined in package `cdn` and cannot be modified
  = help: decouple from the package type — define a local type and convert:
  |
  |   class LocalAvatar includes From[cdn.Avatar], Eq
  |     url: String
  |     def from(a: cdn.Avatar) -> Self
  |       LocalAvatar(url: a.url)
  |
  = help: store `LocalAvatar` instead of `cdn.Avatar` in your class
```

This diagnostic pattern applies to all protocol traits, not just Eq.
Whenever a trait cannot be satisfied because of a foreign type in the
chain, the compiler guides the developer toward decoupling via `From[T]`
into a local type they control.

### Stdlib

`Int`, `Float`, `String`, `Bool` include `Eq`. `List[T]` includes `Eq`
when `T includes Eq`.

## 5. Ord — Ordering

### What It's For

Ord answers "which of these two things comes first?" It makes `<`, `>`,
`<=`, `>=` work on user types, and it makes `sort()`, `min()`, `max()`,
binary search, priority queues, and tree maps work.

Without Ord, sorting is magic that only works on primitives. With Ord,
any type can participate.

### Trait Definition

```
enum Ordering
  Less
  Equal
  Greater

trait Ord includes Eq
  def cmp(other: Self) -> Ordering
```

`Ord includes Eq` because ordering implies equality — if you can tell
which of two things comes first, you can tell if they're the same.
Including `Ord` gives you `Eq` automatically.

When a class includes `Ord` but doesn't define `eq()`, the compiler
auto-derives `eq` from `cmp`:

```
def eq(other: Self) -> Bool
  cmp(other: other) == Ordering.Equal
```

### Operator Desugaring

- `a < b` desugars to `a.cmp(other: b) == Ordering.Less`
- `a > b` desugars to `a.cmp(other: b) == Ordering.Greater`
- `a <= b` desugars to `a.cmp(other: b) != Ordering.Greater`
- `a >= b` desugars to `a.cmp(other: b) != Ordering.Less`

One method powers all four operators.

### No PartialOrd

Same reasoning as no PartialEq. Rust has `PartialOrd` because `f64`
can't be totally ordered (NaN is incomparable). Aster handles this as
a runtime behavior — Float includes Ord, NaN comparisons return a
documented deterministic result (NaN sorts last), move on.

### Auto-Derive

When a class writes `includes Ord` without defining `cmp()`, the
compiler generates field-by-field comparison in declaration order.
First field is the primary sort key, second field breaks ties, and
so on. All fields must include `Ord`.

```
class Task includes Ord
  priority: Int
  created_at: Int
  title: String
# compiler generates: compare by priority, then created_at, then title
```

Manual implementation for custom ordering:

```
class Task includes Ord
  priority: Int
  created_at: Int
  title: String

  def cmp(other: Task) -> Ordering
    # higher priority first (reverse order)
    if priority > other.priority
      Ordering.Less
    else if priority < other.priority
      Ordering.Greater
    else
      # same priority — older task first
      created_at.cmp(other: other.created_at)
```

### Foreign Type Diagnostic

Same pattern as Eq — if a field's type is foreign and lacks Ord, the
compiler guides toward `From[T]` decoupling.

### Stdlib

`Int`, `Float`, `String`, `Bool` include `Ord`. `List[T]` includes
`Ord` when `T includes Ord` (lexicographic comparison).

## 6. Printable — String Representation

### Trait Definition

```
trait Printable
  def to_string() -> String
  def debug() -> String
    to_string()
```

Two methods, one trait. `to_string()` is for users. `debug()` is for
developers and defaults to calling `to_string()`.

### Where Each Is Used

- `to_string()` — string interpolation (`"value is {x}"`), `log()`,
  user-facing output
- `debug()` — REPL inspection, diagnostic messages, error context

String interpolation always calls `to_string()`. A future interpolation
sigil (design TBD) may call `debug()` for developer output.

### Auto-Derive

When a class writes `includes Printable` without defining either method,
the compiler generates a structural representation for `to_string()`:
`ClassName(field1: value1, field2: value2)`. All fields must include
`Printable`.

`debug()` defaults to `to_string()`. Override either or both:

```
class Point includes Printable
  x: Int
  y: Int
# auto-derived to_string(): "Point(x: 3, y: 4)"
# debug() defaults to same

class Point includes Printable
  x: Int
  y: Int

  def to_string() -> String
    "(" + x.to_string() + ", " + y.to_string() + ")"

  def debug() -> String
    "Point(x: " + x.to_string() + ", y: " + y.to_string() + ")"
```

### Stdlib

All primitives include `Printable`. `List[T]` includes `Printable`
when `T includes Printable`.

## 7. Iterable — Iteration and Collection Vocabulary

### Design Inspiration

Ruby's `Enumerable` module: implement one method (`each`), get dozens
of collection methods for free. The compiler tree-shakes unused methods
— it's a buffet, you only pay for what you use.

### Trait Definitions

```
trait Iterator[T]
  def next() -> T?

trait Iterable[T]
  def each() -> Iterator[T]

  # Transform
  def map(f: (T) -> U) -> List[U]
  def flat_map(f: (T) -> List[U]) -> List[U]

  # Filter
  def filter(f: (T) -> Bool) -> List[T]
  def reject(f: (T) -> Bool) -> List[T]

  # Search
  def find(f: (T) -> Bool) -> T?
  def any(f: (T) -> Bool) -> Bool
  def all(f: (T) -> Bool) -> Bool
  def none(f: (T) -> Bool) -> Bool

  # Reduce
  def reduce(init: U, f: (U, T) -> U) -> U
  def count() -> Int

  # Access
  def first() -> T?
  def last() -> T?
  def take(n: Int) -> List[T]
  def skip(n: Int) -> List[T]

  # Order (requires T includes Ord)
  def min() -> T?
  def max() -> T?
  def sort() -> List[T]
  def sort_by(f: (T) -> U includes Ord) -> List[T]

  # Group
  def group_by(f: (T) -> K) -> Map[K, List[T]]
  def zip(other: Iterable[U]) -> List[Pair[T, U]]

  # Convert
  def to_list() -> List[T]
  def to_map(f: (T) -> Pair[K, V]) -> Map[K, V]
```

All default implementations are built on `each()`. A class only needs
to implement `each()` to get the full vocabulary. Override any method
for performance — a `List` can implement `first()` as index access
instead of iterating.

### Iterator Uses T? for Completion

`next() -> T?` returns the next value, or `nil` when done. Aster's
nullable type is the natural "done" signal — no `StopIteration`
exception, no separate `has_next()` boolean.

### For Loop Desugaring

`for x in thing` desugars to:

```
let _it = thing.each()
# loop:
#   let _next = _it.next()
#   match _next
#     nil -> break
#     x -> body
```

### Conditional Methods

Some methods in the Iterable vocabulary require additional constraints
on `T` (e.g., `min()` requires `T includes Ord`). The mechanism for
expressing "this default method only exists when T satisfies a
constraint" will be designed during implementation. The intent is
established here; the syntax for conditional default methods is TBD.

### Example Implementation

```
class Range includes Iterable[Int]
  start: Int
  end: Int

  def each() -> RangeIterator
    RangeIterator(current: start, end: end)

class RangeIterator includes Iterator[Int]
  current: Int
  end: Int

  def next() -> Int?
    if current >= end
      nil
    else
      let val = current
      current = current + 1
      val
```

```
for i in Range(start: 0, end: 5)
  log(message: i.to_string())

Range(start: 1, end: 100)
  .filter(f: -> x: x % 2 == 0)
  .map(f: -> x: x * x)
  .take(n: 5)
```

### Stdlib

`List[T]`, `Map[K, V]`, `String`, and `Range` include `Iterable`.
`Map[K, V]` iterates over `Pair[K, V]`.

## 8. Hash — Invisible, Automatic

### Not a Protocol

Hash is not a trait. Developers never write `includes Hash`, never
implement a `hash()` method, never think about hashing.

### How It Works

If a type includes `Eq`, it is automatically hashable. The compiler
generates a hash function based on the same fields that `eq()` uses.
This is an internal compiler concern, not a language concept.

```
class User includes Eq
  id: Int
  name: String

# User can be a Map key. It just works.
let users = Map[User, String]()
```

`Map[K, V]` requires `K includes Eq`. The compiler handles hashing
internally.

### The Contract

The compiler-generated hash always satisfies: if `a.eq(other: b)` is
true, then `a` and `b` hash to the same value. This is guaranteed
because the hash is derived from the same fields as `eq()`. There is
no way for a developer to break this contract because there is no way
to write a custom hash.

### Hashing Algorithm

The hashing algorithm is an internal implementation detail of the
compiler and runtime. It is not configurable via language syntax or
compiler flags. The algorithm can be swapped by modifying the compiler
source code. No public interface for custom hashers will be provided
unless community demand warrants it.

### Why No Trait

- Writing correct hash functions is hard — most developers get it wrong
- The hash/eq contract is a common source of subtle bugs when both are manual
- The hashing algorithm is a runtime optimization concern, not a type concern
- Exposing it adds surface area with no practical benefit for application code

## 9. Default — Deferred

Field defaults on classes and parameter defaults on functions cover the
construction case:

```
class Config
  retries: Int = 3
  timeout: Int = 30

Config()    # uses field defaults
```

The remaining use case — generic code that needs a zero value of an
unknown type — is real but niche. A `Default` protocol may be added
in the future if generic programming patterns demand it. The shape
would follow `From` as a compiler intrinsic: `Type.default()`.

## 10. Foreign Type Diagnostic Pattern

Whenever a protocol trait cannot be satisfied because a field's type
is foreign and does not include the required trait, the compiler
produces a diagnostic that:

1. Identifies the foreign type and its package
2. States that the foreign type cannot be modified
3. Guides the developer to decouple via `From[T]` into a local type
4. Shows a concrete code example of the local type with `From` and the
   needed protocol trait

This pattern applies uniformly to Eq, Ord, Printable, Iterable, and
any future protocol trait. The message is never just "type X lacks
trait Y" — it teaches the architecture: own your types, convert at
the boundary.

Example for any trait (Eq, Ord, Printable, etc.):

```
Error[E0XX]: cannot derive {Trait} for `{Class}`
  --> {file}:{line}:{col}
  |
N |   field_name: pkg.ForeignType
  |   ^^^^^^^^^^^^^^^^^^^^^^^^^^^ `pkg.ForeignType` does not include {Trait}
  |
  = note: `pkg.ForeignType` is defined in package `pkg` and cannot be modified
  = help: decouple from the package type — define a local type and convert:
  |
  |   class Local{Type} includes From[pkg.ForeignType], {Trait}
  |     field1: ...
  |     def from(value: pkg.ForeignType) -> Self
  |       Local{Type}(field1: value.field1)
  |
  = help: store `Local{Type}` instead of `pkg.ForeignType` in your class
```

## 11. Summary of Decided Design

### Protocols

1. **From[T]** — construction protocol, include on target type you own,
   invoked via `Type.from(value: x)` compiler intrinsic
2. **Into[T]** — instance method protocol, include on source type you own,
   invoked via `x.into()` with expected-type resolution
3. **From implies Into** — compiler auto-derives `.into()` on the source
   type when the target includes `From[T]`
4. **Fallible conversion** — add `throws` to `from()`/`into()`, no separate
   TryFrom/TryInto
5. **From[T] is the only custom initializer** — no custom constructors
6. **Eq** — `def eq(other: Self) -> Bool`, desugars `==` and `!=`
7. **No PartialEq** — one equality trait, Float NaN is documented behavior
8. **Ord** — `def cmp(other: Self) -> Ordering`, desugars `<` `>` `<=` `>=`
9. **Ord includes Eq** — ordering implies equality, auto-derived from `cmp`
10. **No PartialOrd** — one ordering trait, Float NaN sorts last
11. **Printable** — `to_string()` for users, `debug()` for developers
12. **String interpolation** uses `to_string()`, REPL uses `debug()`
13. **Iterable[T]** — implement `each()`, get full Ruby-style vocabulary
14. **Iterator[T]** — `next() -> T?`, nullable as completion signal
15. **For loops** desugar to `each()` + `next()`
16. **Tree-shaking** — unused Iterable methods have zero cost
17. **Hash is not a trait** — automatic and invisible, derived from Eq
18. **Hash algorithm** is internal, no public interface
19. **Default** — deferred, field defaults and param defaults cover it

### Auto-Derive Rules

| Trait | Auto-Derive Behavior |
|-------|---------------------|
| Eq | Field-by-field comparison, all fields must include Eq |
| Ord | Field-by-field in declaration order, all fields must include Ord |
| Printable | Structural form `ClassName(field: value)`, all fields must include Printable |
| Hash | Always automatic from Eq, never manual |

### Prerequisites

20. **Parametric traits** — `trait Into[T]`, `trait Iterable[T]`
21. **Self type in traits** — `def eq(other: Self) -> Bool`
22. **Named arguments everywhere** — required on all function calls and
    class construction, matched by name not position, order independent
23. **Ordering enum** — `Less`, `Equal`, `Greater` (requires enum support)

### Cross-Cutting Decisions

24. **Compiler intrinsics for construction protocols** — `Type.from()` is in
    the same category as `Type.fields` and `Type.ancestors`, not a class method
25. **Foreign type diagnostic pattern** — all protocol traits produce
    architecture-guiding diagnostics for foreign type issues
26. **includes is always explicit** — the compiler never infers trait inclusion
    from method signatures alone

## 12. What Was Rejected

- `From[T]` via constructor syntax (`User(pg_row)`) — ambiguous with field construction
- `PartialEq` / `PartialOrd` — type-level NaN handling not worth the complexity
- `TryFrom` / `TryInto` — Aster's `throws` covers fallible conversion
- Manual `hash()` implementations — too error-prone, no benefit
- `Hash` as a visible trait — implementation detail, not a type concern
- `Default` trait (for now) — field defaults cover the construction case
- Positional function arguments — inconsistent with named class construction
- Optional argument naming — "two ways to do something"

## 13. Open Questions

- ~~**Conditional default methods**~~ — Resolved. Iterable vocabulary methods
  (min, max, sort) are injected unconditionally; the Ord constraint is checked
  at the call site in the typechecker (E025).
- ~~**Enum support**~~ — Resolved. Unit enums implemented (BC-4). `Ordering` enum
  with `Less`, `Equal`, `Greater` is built-in.
- ~~**Parametric trait expected-type resolution**~~ — Resolved. When a class
  includes multiple parametric traits of the same name (e.g., `Into[Fahrenheit],
  Into[Kelvin]`), the compiler disambiguates `.into()` using the expected type
  from context (let binding annotation, function argument type). If ambiguous,
  the compiler reports an error asking for a type annotation.
- **Lambda syntax in named args** — `list.map(f: -> x: x * 2)` may need
  refinement for ergonomics. Syntax TBD.
- **String interpolation** — the `"value is {x}"` syntax and its interaction
  with `to_string()` needs a separate design.
